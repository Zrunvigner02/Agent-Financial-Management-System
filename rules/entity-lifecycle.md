# 实体生命周期规则（离职 / 品牌停做 / 渠道关停）

> 一句话：**历史一个字都不删，未来一天都不多算。**
>
> 老板说「张三离职了」「世家不做了」，系统要做的是**登记一个截止日**，而不是删数据。

---

## 1. 核心概念

`effective_to` = **最后一天仍然有效的日期（含当天）**。

| 老板的话 | 登记成 | 从哪天起不算 |
|---|---|---|
| 张三 11 月 16 日离职 | staff / 张三 / 2026-11-16 | 2026-11-17 |
| 张三 11 月底离职 | staff / 张三 / 2026-11-30 | 2026-12-01 |
| 张三 11 月做完就走（只说月份） | staff / 张三 / 2026-11 | 自动按 11-30 |
| 世家品牌不做了，12 月起不出 | brand / 世家 / 2026-11-30 | 2026-12-01 |

- 只登记日期，**不删除任何凭证、销售行、报表、对话**；
- 停用日之前的数据，怎么查都和原来一样；
- 停用日之后，系统不再**自动产生**这个实体的支出 / 业绩 / 报表行；
- 停用当月，固定支出**按在职天数折算**（可在模板上关掉折算，社保一类通常整月照缴）。

## 2. 四种实体

| type | 名称来源 | 典型场景 |
|---|---|---|
| `staff` | 员工姓名（与销售数据 `staff` 字段一致） | 离职、退休、调岗 |
| `brand` | 品牌名（与损益 `brand` 字段一致） | 品牌不做了、暂停代理 |
| `channel` | 渠道名（天猫 / 京东 / 拼多多） | 关店、停投 |
| `store` | 店铺名 | 单店关闭 |

> 名称必须和业务数据里的写法**一模一样**（「张三」≠「张三（运营）」）。不确定时先查：
> `list_entity_status`、`node tools/entity-status.mjs`，或看销售看板里的员工名。

## 3. 各模块口径

| 模块 | 停用后怎么算 | 历史怎么办 |
|---|---|---|
| 固定支出（工资/社保/房租） | 次月起不再生成；停用当月按天折算，分录摘要写明「张三是 2026-11-16 停用，按 16/30 天折算」 | 已生成的凭证一张不动，`recurring_runs` 记录保留 |
| 员工业绩 | 停用日之后的销售不计入该员工 | 原始 `sales_daily` 行全在，历史业绩报表照样出 |
| 损益（品牌维度） | 停用月之后的期间不再入表，结果里列出 `excluded_brands` | 停用月及以前的损益行原样保留 |
| 销售看板 / 报表 | 历史区间照常显示 | 不做任何删除 |
| 智能体 | 回答里会说明「已停用，最后有效日 xx」，并提示历史仍在 | 对话本身留痕 |

**判定只有一条**：`数据日期 <= effective_to` → 仍然算；`>` → 不再算。

## 4. 怎么操作

### 4.1 对智能体说人话

- 「张三 11 月 16 号离职了」
- 「世家品牌 12 月开始不做了」
- 「把李四恢复到在职」

智能体会调 `set_entity_status`（写操作走两阶段：先给摘要，回「确认」才落库）。
它也可以先用 `list_entity_status` 查有哪些人/品牌已停用。

### 4.2 命令行

```bash
node tools/entity-status.mjs                                  # 看全部
node tools/entity-status.mjs --type staff                      # 只看员工
node tools/entity-status.mjs --stop staff 张三 --to 2026-11-16 --reason 离职
node tools/entity-status.mjs --stop brand 世家 --to 2026-11 --reason 品牌不做了
node tools/entity-status.mjs --resume staff 张三
```

### 4.3 接口

```bash
GET  /api/lifecycle?type=staff           # 看状态 + 最近日志
POST /api/lifecycle
{ "type": "staff", "name": "张三", "action": "stop",
  "effective_to": "2026-11-16", "reason": "离职", "prorate": true }
```

旧入口 `POST /api/recurring/:id/resign` 仍可用：它会给模板打「离职」标注，同时按模板里的 `person` 写人员生命周期（最后有效日 = 该月月末）。

## 5. 边界与兜底

- **只给月份**：按该月最后一天算，避免「11 月」被理解成 11-01 而少算整月。
- **重复登记**：同一个人/品牌只保留一行，重复提交只更新日期，不产生多行。
- **恢复**：`action=resume` 清空截止日，状态回 active，历史不受影响。
- **只在模板上打「离职」标注**：仍然兼容，折算成「该月月初前一天」，即该月起不再生成（旧口径）。
- **没登记 = 有效**：系统默认一切正常，绝不因为查不到状态就少算。
- **停用但没给日期**：不按日期卡（相当于只做标记），不建议这么用。

## 6. 留痕

- `entity_status`：当前状态（每个实体一行）
- `entity_status_log`：每次停用 / 恢复都追加一条，含操作人、时间、原因
- 固定支出的折算会写进凭证分录摘要，翻凭证就能看到为什么这个月金额变了

## 7. 禁止项

1. 不因为离职就删凭证、删销售行、删报表 —— **一次都不行**。
2. 不把 `effective_to` 当成「停用开始日」用；它是**最后有效日**，含当天。
3. 不在折算时手动凑数：借贷差额由程序补到金额较大的一侧，不允许出现借贷不平。
4. 不把停用当删除：查不到记录时按「有效」处理，避免静默少算。

## 8. 自检

```bash
npm run test:lifecycle    # 26 项：离职后不生成 / 当月折算 / 历史不动 / 业绩排除 / 品牌停用 / 恢复 / 留痕
```
